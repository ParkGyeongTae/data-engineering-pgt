# 현업에서는 언제 Zeppelin을 쓸까?

> When Do Companies Actually Use Apache Zeppelin?

## 들어가며

Apache Zeppelin에 기여하려다 보면 코드는 눈에 익어도, 정작 현업에서 이걸 어떻게 쓰는지는 잘 그려지지 않을 수 있다.

DE(Data Engineer)로 커리어를 시작해 지금은 DAE(Data Analytics Engineer)로 일하면서 겪은 경험을 바탕으로 이 글을 정리했다. 회사마다 규모·조직·도메인이 달라 정답은 아니지만, 최대한 일반적인 그림으로 구성했다.

데이터 플랫폼이 어떻게 돌아가는지 보면, Zeppelin이 어디서 왜 쓰이는지 자연스럽게 이해할 수 있다. 이 글에서는 데이터가 흐르는 순서를 따라 세 가지를 다룬다.

| 단계 | 질문 |
| --- | --- |
| **수집** | 운영계 데이터를 어떻게 분석계로 옮길까? |
| **처리** | 커진 데이터를 무엇으로 처리할까? — 로컬 파이썬의 한계 |
| **조회** | Athena, Superset, Tableau, Hue… 그중 Zeppelin을 고르는 순간 |

---

## 1. 수집 — 운영계 데이터를 분석계로 복제

### 문제

- 백엔드는 보통 데이터를 **RDB**에 저장한다. 행 단위 처리가 중요하기 때문에 합리적인 선택이다.
- 그런데 우리가 분석하려는 데이터도 결국 이 운영 DB 안에 있다.
- 서비스에 연결된 운영 DB에 분석 쿼리를 직접 날리면 **부하·락·장애 전파**로 이어질 수 있다.
- 분석 쿼리는 한 명이 아니라 **전체 사용자·특정 집단·특정 페이지 단위**로 조회하기 때문에, 읽기만으로도 부하가 생긴다.

### 해결

- 운영계 데이터를 **S3 같은 별도 저장소로 복제·적재**해서, "분석용 데이터가 준비되는 곳"을 따로 둔다.
- 어느 정도 규모의 회사는 이 복제를 **데이터 엔지니어**가 담당한다. 두 데이터베이스 간 동기화, 나아가 정합성을 맞추는 업무까지 포함한다.
- 그냥 파일로만 쌓아두면 못 쓴다. **Hive 형식(스키마 + 파티션)** 으로 저장해서, RDB를 쓰듯 쿼리로 조회할 수 있게 유지한다.
- 별도 경로도 있다. **로그성 데이터**는 클라우드 스토리지 비용이 경제적이라, RDB를 거치지 않고 S3에 바로 적재하는 것도 합리적인 판단이다.

> 다음 질문은, 그렇게 쌓인 데이터를 **어떻게 처리할 것인가**다.

---

## 2. 처리 — 로컬 파이썬의 한계

- S3에 데이터가 쌓이기 시작하면, 처음엔 로컬 **pandas**로 충분히 처리할 수 있다.
- 하지만 pandas는 데이터를 **메모리에 전부 올려서** 처리하기 때문에, 데이터가 커지면 **메모리 부족(OOM)** 으로 아예 처리가 안 되는 시점이 온다.
- 메모리를 넘기지 않더라도, **단일 프로세스**라 처리 시간이 몇 시간씩 걸리는 배치가 생기기 시작한다.

그래서 도구가 바뀐다.

- **Spark**: 데이터를 여러 노드에 나눠 **분산 처리**함으로써 메모리·처리 시간 문제를 동시에 해결한다.
- **EMR**: 그 Spark 클러스터를 직접 구축·운영하지 않고, **관리형**으로 필요할 때 띄우고 내릴 수 있게 해주는 인프라다.

> 다음 질문은, 그렇게 처리된 **큰 데이터를 어떻게 조회·분석할 것인가**다.

---

## 3. 조회 — 도구 비교

이 데이터를 조회하는 사람도 다양하다.

- 분석계에 있는 데이터를 조회하는 **개발자**
- 푸시 성과를 빠르게 확인하고 싶은 **PM**
- 요청받은 분석 업무를 해결하려는 **데이터 분석가**

같은 데이터라도 **조회하는 사람·목적**에 따라 쓰는 도구가 다르다. 그리고 그 선택지의 폭은 **회사 규모**가 먼저 갈라놓는다.

### 먼저, 회사 규모가 판을 가른다

- **규모가 작은 회사**에서는 지급받은 노트북(로컬)에서 직접 데이터를 조회·처리하는 경우가 많다. 개인 환경에서 SQL을 날리고 파이썬으로 돌려도 별문제가 없다.
- **규모가 있는 회사**에서는 보안을 이유로 **로컬에서의 데이터 접근 자체를 막는다.** 대신 데이터에 접근할 수 있는 시스템 — **Superset · Zeppelin · Hue** 같은 사내 플랫폼 — 을 제공한다. 데이터는 회사가 관리하는 서버 안에 머물고, 사용자는 브라우저로 그 시스템에 접속해서 일한다.

즉 규모가 커질수록 선택지는 **"브라우저로 접속하는 공유 시스템"** 안에서 결정된다. 그럼 그 시스템들은 서로 어떻게 다를까.

### 도구들을 하나의 축에 놓으면

| 도구 | 특징 |
| --- | --- |
| **Athena** | SQL로 가볍게 조회 |
| **Superset / Tableau** | 대시보드·BI 리포트 |
| **Hue** | 하둡 생태계 쿼리 실행 |
| **Jupyter** | 범용 노트북. 로컬·개인 분석에 강하지만, Spark 연동과 협업 공유는 상대적으로 약함 |
| **Databricks** | 관리형 Spark 노트북 플랫폼. Zeppelin + EMR 조합과 가장 직접적으로 경쟁하는 상용 대안 |
| **Zeppelin** | Spark 노트북 기반, 코드 + 시각화 결합, 탐색적 분석 과정을 팀과 공유 |

- **Athena**는 조회(SQL)만 한다. 결과를 가공하거나 이어서 탐색하기 어렵다.
- **Superset / Tableau**는 이미 정해진 지표를 **대시보드**로 보여준다. "정답이 정해진" 리포트에 강하지, 아직 뭘 볼지 모르는 탐색에는 약하다.
- **Hue**는 하둡 쿼리 실행 창구에 가깝다.

즉 대부분의 도구는 **조회 아니면 대시보드** 한쪽에 특화돼 있다. 그런데 현업 분석은 그 사이, **"쿼리로 뽑고 → 코드로 가공하고 → 바로 시각화해서 → 다음 가설을 세우는"** 탐색 과정 자체다. 이 과정을 한 곳에서 하려면 **노트북**이 필요하고, 후보는 Jupyter · Databricks · Zeppelin으로 좁혀진다.

여기서 **Jupyter**는 로컬·개인 성향이 강해, 앞서 본 보안 이유로 규모 있는 회사에서는 밀려난다. 남는 실질 후보는 **Databricks**와 **Zeppelin**이다.

### Zeppelin만의 강점

노트북 후보 중에서 Zeppelin이 가진 결은 이렇다.

- **여러 인터프리터를 한 노트북에서.** 한 노트북 안에서 문단마다 Spark(Scala)·PySpark·SQL·Markdown을 섞어 쓸 수 있다. 데이터 처리와 설명, 시각화가 한 화면에 이어진다.
- **내장 시각화.** 별도 라이브러리 없이 쿼리 결과를 표·차트로 바로 전환한다.
- **문단 단위 공유.** 노트북 링크만 넘기면 상대는 해당 문단만 실행해 결과를 볼 수 있다.

> **구체적인 장면 하나.** PM이 어제 보낸 푸시의 오픈율을 확인하고 싶다. 예전 같으면 데이터 분석가에게 요청 → 대기였지만, 이제는 데이터 엔지니어가 만들어 둔 Zeppelin 노트북 링크를 열고, 날짜 문단만 바꿔 **셀 하나를 실행**하면 끝난다. SQL 결과가 바로 차트로 뜨고, PM은 그 화면을 팀 채널에 공유한다. AWS 키도, 로컬 환경 세팅도 필요 없다.

### 그래서, Zeppelin을 선택하는 순간

남은 비교는 **접근 권한**, 그리고 **Zeppelin vs Databricks**다.

- 로컬 파이썬(Jupyter 포함)이 밀려나는 결정적 이유도 결국 **접근 권한**이었다. 개인이 AWS 접근 권한을 직접 쥐고 다뤄야 해서, 데이터 엔지니어가 아닌 사람에게까지 권한이 퍼지며 **보안·거버넌스 부담**이 커진다.
- **Zeppelin 같은 공유 노트북 플랫폼**은 개인 AWS 키 없이 접근을 **중앙에서 관리**해 이 문제를 해결한다.
- 마지막 남은 대안인 **Databricks**와 비교하면, **Zeppelin + EMR** 조합은 오픈소스라 별도 라이선스 비용 없이 **필요할 때만 클러스터를 띄우고 내릴 수 있다.** 비용·거버넌스를 조직이 직접 통제하고 싶을 때 선택지가 된다.

> 정리하면, Zeppelin은 **"Spark 연동이 필요한 규모 + 접근 권한의 중앙 관리 + 비용 통제"** 가 동시에 요구되는 지점에서 선택된다.

---

## 마무리

오늘의 흐름을 다시 보면:

**운영 DB 복제 → Spark/EMR로 분산 처리 → 처리된 데이터를 조회하는 여러 방식 중 하나로 Zeppelin이 선택된다.**

다시 처음 질문으로 돌아가면 — Zeppelin에 기여하려는 우리에게 이 그림이 왜 중요할까.

현업에서 어디에 쓰이는지 알면, 코드의 어떤 부분이 **실제로 중요한 기능인지** 감이 잡힌다. 인터프리터 연동, 시각화, 노트북 공유·권한처럼 사용자가 매일 부딪히는 지점이 곧 **기여 가치가 큰 지점**이다. 사용 맥락을 알고 코드를 보면, "고칠 수 있는 곳"이 아니라 "고치면 도움이 되는 곳"이 보이기 시작한다.
